## Prologue: getting the skills to load

Before any design work, three problems had to be cleared.

1. **Skills nested under category folders.** `.claude/skills/engineering/domain-modeling/` etc. Claude Code scans exactly one level deep (`.claude/skills/<name>/SKILL.md`), so nothing loaded. The layout came from an OpenAI-format skill package (`agents/openai.yaml` in each folder), which does support category nesting. Fixed by flattening.

2. **`/setup-matt-pocock-skills` reported "does not exist".** The skill file was valid — good frontmatter, correct name, LF endings, and `disable-model-invocation` confirmed supported in Claude Code 2.1.141. The cause was timing: the folder arrived on disk *after* session start, and the slash-command registry is built at startup. Fixed by restarting.

3. **Skills relocated to `.agents/skills/`.** A package manager (`skills-lock.json`, sourcing `mattpocock/skills`) installed 37 skills to a directory Claude Code doesn't scan. Fixed with a symlink: `.claude/skills -> ../.agents/skills`, which Claude Code follows.

`/setup-matt-pocock-skills` then ran twice — first when `triage` was not installed (Section B skipped), then again after it appeared, to add the label vocabulary. Produced `CLAUDE.md`, `docs/agents/issue-tracker.md`, `docs/agents/domain.md`, `docs/agents/triage-labels.md`, and the five triage labels on GitHub.

### Round 2 — the model

| | Question | Recommended | **Chosen** |
|---|---|---|---|

## Ticket: What is the v1 YAML schema? (#6)

| | Question | Recommended | **Chosen** |
|---|---|---|---|
| Q1 | Nested or flat records? | nested | **nested** |
| Q2 | Which end declares a Reporting Line? | (a) manager on the Position | **"remove reporting manager from scope"** |
| Q3 | How is occupancy expressed? | (a) `occupant:` on the Position, people declared once | **(a)** |
| Q4 | One file or many? | (a) one file | **two files: `<company>-teams.yaml` + `<company>-employees.yaml`** |

**Q2 was a second scope cut.** Checked against the objectives before acting: none of the five requires reporting lines — objective five is explicitly about teams — so teams-only is coherent. It lands on round one's rejected option (c), but consistently, since plural team membership now comes from Q12 instead. Unlike Path identity, it is cheaply reversible: an optional `manager:` field is purely additive.

Weakening noted without reopening: Positions were chosen partly because an empty seat would sever the reporting chain. There is no chain now.

`CONTEXT.md` lost `Reporting Line` and `Manager`, gained `Occupant`.

## Ticket: How are ordinal suffixes assigned? (#7)

A finding reframed this ticket before any question was asked: **nothing in v1 references a Position by Path.** Teams nest structurally, occupancy points at an email, and the one field that would have carried a Path — `manager:` — went out of scope with reporting lines.

> "Let's leave out ordinal suffixes."

That removed the only thing making a Path unique. One question confirmed the reading:

| | Question | Recommended | **Chosen** |
|---|---|---|---|
| Q1 | Do duplicate titles survive the cut? | (a) yes — Path demoted to a display label | **(a)** |

**Resolution: Positions have no identity in v1.** Affordable because no field consumes one. `CONTEXT.md` demoted `Path` from "a Position's identity" to a location label. Two Out-of-scope entries on the map that had justified themselves by appealing to Path identity were rewritten to stay true.

## Ticket: Which fields do Position and Employee records carry? (#9)

Principle named and applied: **a field with no v1 consumer is waste.**

| | Question | Recommended | **Chosen** |
|---|---|---|---|
| Q1 | Team display name separate from key? | (a) key only | **(a)** |
| Q2 | What does each file declare at root? | (b) both declare `org` and `version` | **(b)** |
| Q3 | Position fields? | (a) `title` + `occupant` | **+ `description` (optional)** |
| Q4 | Employee fields? | (a) `email` + `name` | **+ arbitrary attributes, including nested objects** |

`version:` was the one deliberate breach of the no-consumer principle: its consumer is future tooling reading today's files.

Follow-up, surfaced by Q4:

| | Question | Recommended | **Chosen** |
|---|---|---|---|
| Q1 | Custom attributes flat or namespaced? | (b) namespaced under `attributes:` | **(a) flat** |

Concrete risk accepted: `location: Berlin` written today as a custom attribute could collide with a reserved `location:` in v2. `version:` is the mechanism that makes such a collision detectable.

Recorded as deliberate: **Position is a closed set; Employee is open.**

|---|---|---|---|
| Q1 | Does a JSON Schema ship? | (a) yes | **(a)** |
| Q2 | Are unknown keys an error? | (a) yes | **strict in teams.yaml, permissive in employees.yaml** |

## Ticket: Author the JSON Schemas (#11)

Written: `schemas/teams.schema.json` (strict) and `schemas/employees.schema.json` (permissive), JSON Schema draft 2020-12.

**Verified against 19 cases**, all passing — 13 for the teams file, 6 for the employees file, covering every decided rule in both the accepting and rejecting direction.

**Correction issued.** The claim in #10 that "duplicate keys are invalid YAML" is parser-dependent: PyYAML accepts them and silently keeps the last. The map-over-list decision still stands — a list leaves both contradictory records present and undetectable — but a validator must check duplicates explicitly. The shipped schema description was reworded.

Four interpretations recorded for correction: the employees map enforces a loose email pattern on keys; `employees:` is optional; `version` is `const: 1`; `org` forbids `/`.

## Ticket: Rebuild the acme example (#8)

`acme-teams.yaml` and `acme-employees.yaml` — 12 Positions across 6 Teams, 9 Employees, both validating cleanly.

Every case the model exists for is exercised: three vacancies; `priya@acme.com` holding two Positions across two Teams; two nesting depths; a Team with both sub-Teams and Positions; a Team with only sub-Teams; an empty Team; two shared Paths; an Employee with no Position; nested custom attributes.

**Finding:** a Position cannot exist outside a Team, so the CEO needs an `Executive` Team. Follows correctly from the model, but nothing had said it out loud.

## The v1 format

```yaml
# acme-teams.yaml — strict
org: ACME
version: 1
teams:
  retail:
    teams:
      OrderManagement:
        positions:
          - title: EngineeringManager
            occupant: priya@acme.com
          - title: SeniorBackendEngineer     # vacant
```

```yaml
# acme-employees.yaml — permissive
org: ACME
version: 1
employees:
  priya@acme.com:
    name: Priya Raman
    location: Berlin
```

## After the map

Work that followed the map's completion. None of it was wayfinder work — no tickets, no grilling rounds — but it is what turned the spec into something usable.

### README rewritten

The original README had four claims the spec had made false: a single `<zyz>-OrgChart.yaml` (also a typo for `xyz`), the implication that an "org chart" carries reporting lines, no separation between ambition and delivery, and objective four reading as a feature when only `git diff` serves it.

Rewritten with the five objectives kept verbatim, plus a Status section and an explicit **Not in v1** list, so an ambition cannot be mistaken for a delivered feature. Two things deliberately left alone: the "generate diagrams from it" tagline, since that is what the project is *for*; and the project name, which is now inaccurate in the same way the old filename was — with no reporting lines this generates team-structure diagrams, not org charts.

### Three generated example organizations

Requested: 10, 30 and 100 Teams; 3–7 positions per team; a Domain Architect on parents with 3–5 children; a System Architect additionally on grandparents.

Generated programmatically so the rules hold exactly, then verified per team: exactly one ProductOwner, 3–7 core positions, every parent with 3–5 children and one DA, every grandparent with an SA and every non-grandparent without, no `/` anywhere, every occupant resolving.

| | Teams | Positions | Employees | Vacant | DA | SA | Depth |
|---|---|---|---|---|---|---|---|
| acme-small | 10 | 48 | 45 | 3 | 2 | 1 | 3 |
| acme-medium | 30 | 152 | 144 | 8 | 6 | 1 | 3 |
| acme-large | 100 | 505 | 477 | 28 | 24 | 5 | 3 |

Two defects caught by verification rather than by the request:

- **`acme-small` initially had no SystemArchitect at all.** At ten teams the tree came out two levels deep, so nothing had grandchildren and the SA rule never fired. Fixed by giving it one top-level division instead of two, forcing three levels. Structural, not incidental: an SA can only exist at ten teams if the org is deliberately deep rather than wide.
- **Indentation drifted wider at each nesting level**, 8 spaces where 6 belonged, compounding downward. Valid YAML, but these files exist to demonstrate that the format is pleasant to read by hand.

Also chosen without being asked, and flagged as such: roughly 5% of seats left vacant, and no employee holding two positions (so plural team membership is demonstrated only by the hand-written `acme-tiny`).

### `scripts/validate.sh`

Validates one file, or both files of an organization from a bare prefix. Exit codes distinguish valid (0), a validation failure (1) and usage or missing dependencies (2).

Two things beyond the literal request, both flagged at the time:

- **It rejects duplicate YAML keys.** This is the hole found while authoring the schemas: PyYAML silently keeps the last of two identical employee emails, so a file that has quietly lost a record still validates against the schema. JSON Schema cannot see it.
- **It handles its own dependencies.** The system `python3` had neither `pyyaml` nor `jsonschema`, so a naive script would have crashed. It searches `$ORGCHART_PYTHON`, a local `.venv`, then `python3`, and prints what to run instead of a traceback. `--setup` creates the venv.

Later moved from the repo root into `scripts/`, which needed three path fixes rather than a plain `mv`: schemas resolved via the repo root, the venv relocated out of `scripts/`, and the usage text updated.
